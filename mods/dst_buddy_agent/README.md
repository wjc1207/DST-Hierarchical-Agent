# DST Buddy Agent 0.7.0

独立服务端伙伴模组，每位玩家支持两个有名字的原版威尔逊，自行生成并绑定，无需 T-mod。服务器管理归属和执行动作；各玩家自己的客户端与本机 Python 调用自己的 DeepSeek，API Key 不进入模组、不发送给服务器。

## 安装与最小实测

1. 将本目录安装为 `mods/dst_buddy_agent`，在世界的**服务端模组**中启用 **DST Buddy Agent**，重新进入世界。参与客户端需安装同版模组。同时使用两套模组时，更新至同批次版本。`@自己` 交给角色操控，`@伙伴名` 和 `@all` 交给伙伴。
2. 在安全陆地、角色存活时，点游戏 HUD 右侧的「伙伴」展开面板，再点「召唤伙伴」并输入名字。也可以在聊天框输入 `/buddy summon 一号`，再用 `/buddy summon 二号` 创建第二个。模组优先复用自己已有或附近可绑定的威尔逊，没有时在附近 2–4 单位安全陆地生成一个；成功后默认跟随。不需要辅助模组或控制台。
   按住「伙伴」右边的小按钮可以上下拖动入口。松手后会在本机保存位置，面板会在入口下方展开。
3. `/buddy stay` 原地待命；`/buddy follow` 恢复跟随；`/buddy stop` 立即中断当前安排。重复 `/buddy summon` 不会重复生成；释放或断线后仍优先找回本次会话中自己的伙伴，不受主人距离限制，也不会瞬移。已有伙伴死亡时会说明原因，不直接生成替身。
4. 面板显示名册和当前行为。选「全体」或单个伙伴后，可以「停止并待命」或「跟随我」。选中单个伙伴可召回或解除绑定。命令行也支持 `/buddy list`、`/buddy status`、`/buddy stop @一号`、`/buddy release @二号`。不带 @ 的手动命令作用于所有已绑定伙伴。

这些手动行为不需要 Python 或 API Key。统一入口为 `/buddy summon`：找回自己的伙伴、绑定附近可用的威尔逊，没有时生成。`/buddy bind` 仅为兼容别名，行为完全相同。仅主动召唤时生成，不会为每个加入的玩家自动生成；排除真实玩家、其他人的专属伙伴和其他 AI 管理的实体。

绑定后会创建主人专属的原版全局地图图标，显示威尔逊头像和对应伙伴名字，并由服务端持续跟踪位置。私人 `maprevealer` 每 1 秒向主人共享伙伴当前位置附近的地形；随着伙伴移动逐步开图，已揭开的地形保留，不回补历史轨迹，也不直接读取 AI 的地图记忆。远离后仍可定位及接收共享，无需组队模组、Python 或模型调用。解除绑定、主人离线或实体删除时停止；不跨洞共享。更新 Lua 后重进世界并 `/buddy summon` 即可。

## 启动自己电脑上的 AI

0.5.1 保存服务端返回的匹配建筑 ID 到达回执；即使后续观察短暂落到 3 单位边界外，也不重复提交同一次已完成的返回。规划错误增加 `planning_detail` 阶段信息和具体原因，记录前移除实际 API Key，不记录原始请求或完整模型正文。本批需重进世界并重启 Python。

以下命令在 **本仓库根目录**运行。使用原项目的 Python 环境与 `python/requirements-mcp.txt`。

首次配置本机回环桥接（安装脚本已为当前开发电脑执行此步骤）：

```powershell
python python/mcp_server/companion_server.py --configure-only --write-mod-config "C:\Program Files (x86)\Steam\steamapps\common\Don't Starve Together\mods\dst_buddy_agent\scripts\jev_companion_config.lua"
```

本地传输 token 存在工程 `logs/companion_bridge.json`，模组只保存相同的本地传输 token；它不是模型 API Key。每台电脑单独执行配置，再重进世界。分发包内默认关闭本机 HTTP，不能拿服主的配置当作所有玩家的配置。

在自己电脑的 `.env` 配置 `DEEPSEEK_API_KEY`，可选 `DEEPSEEK_API_URL`、`DEEPSEEK_MODEL`，然后运行：

```powershell
python python/mcp_agent/companion_agent.py --execute
```

该入口独立使用端口 **8766**，不启动旧玩家控制程序。未加 `--execute` 时只观察，不调用模型或自动操作。仅在有玩家新需求、看板需要继续推进或操作失败时调用模型，待命期间不产生轮询式模型调用。

游戏中先召唤并查看名册，再输入（普通聊天方式需 `/buddy ai`）：

```text
/buddy do @一号 收集三根草，然后回到我旁边
/buddy do @二号 收集两根树枝，然后回到我旁边
/buddy do @全体 停止
```

默认只接收带 `/buddy do` 的明确需求。打开面板的「聊天监听」（或输入 `/buddy ai`）后，聊天以 `@伙伴名` 或 `@全体`（也可用 `@all`）开头即可派活。普通聊天照常发送。带目标的短命令如 `@全体 停止` 立即中断动作，无需等待模型。关闭开关或输入 `/buddy ai off` 可以关闭监听。伙伴回复通过自己的 talker 说话，主人本地聊天也显示 `[Companion] 伙伴名字：...`。

游戏聊天中的 `@伙伴名` 消息触发后台规划。伙伴继续执行现有看板，模型可以只回复，也可以在当前动作结算后更新看板。面板的「停止并待命」与 `/buddy stop` 立即停止指定伙伴；`/buddy do` 保留显式指令入口。各伙伴完成自己的贡献后回复并恢复跟随；单人完成不代表全队目标完成。模型确认最多复查三轮，连续失败也有上限，避免反复空转消耗 token。

## 第一版能力范围

- 主人身份由实际 RPC 发送玩家确定；一名玩家最多绑定两名有唯一名字的伙伴。名字在召唤时设置，1–12 字，不含空格或 @，不能使用全体／all／自己；使用 `/buddy list` 查询。
- 跟随、待命、停止、前往附近陆地坐标。
- 拾取附近可拾取物品；采集草、树枝、普通浆果丛、胡萝卜和芦苇等白名单资源。必须有真实背包增量才算采集成功。
- 独立的伙伴生命、饥饿、理智、背包、主人距离、附近资源与执行状态回传。
- 装备携带物品；使用斧头砍常见树、使用鹤嘴锄挖普通石矿／金矿／冰矿，再拾取实际掉落物。
- 查询伙伴自己的原版配方与科技，普通物品制作及陆地建筑放置，包含绳子、木板、石砖等中间材料。制作验证真实库存增加，建筑验证对应区域内的实体。
- 本机 DS 与原客户端共用的目标看板和完成确认：优先级、依赖、每人最多六项任务、两项专注任务、定时开始。收集数量指伙伴背包里的目标总量，“再收集三根”由模型结合已有数量确定总目标；先后顺序通过 depends_on 表达。
- 原料库存目标默认允许局部搜索；模型可为“只在附近采集”设置 `allow_search:false`。搜索以真实移动时间与距离计入共用预算，耗尽后冷却，空间记忆保留；不能把发现资源或走到落点视为收集完成。

**尚未迁移**烹饪交互、主动点火、设置家／返回家、战斗、全图探索及完整的夜间／生存策略。箱子和锅本体可以按普通配方建造。模型会明确解释能力限制。真实生命、饥饿仍然生效；本版先在白天的安全场地验证。

本次 0.6.4 同时更新 Python 和 Lua，需要重进世界并重启 Python。[动作和实测说明](../../docs/COMPANION_ACTIONS.md)。

普通动作最多运行 8 秒；返回已见建筑最多运行 300 秒，持续 20 秒无移动进展即停止。失去客户端心跳 4 秒后服务端停止动作并待命。主人离开世界会解除绑定，但本次服务器会话中生成的伙伴仍保留主人预约，可重连后 `/buddy summon` 找回。模型控制程序断开时客户端停止 AI 任务；纯手动跟随不依赖 Python。本版尚未实现伙伴跨服务器重启的存档或跨洞迁移；原版玩家实体默认不按普通实体持久化，重开服务器后需重新召唤，不能依赖它保留背包和状态。

## MCP 与日志

```powershell
python python/mcp_server/companion_server.py
```

这是 STDIO MCP 服务，应由 MCP 客户端启动，不与 `companion_agent.py` 同时占用 8766。

| 工具 | 用途 |
|---|---|
| `buddy_observe(buddy_id?)` | 不传 ID 返回队伍；传 ID 返回该伙伴的当前指令、局部感知和观察 ID |
| `buddy_action(op, observation_id, args?)` | `summon/follow/stay/stop/move/collect/equip/unequip/work/craft/place/search/visit_building/give_owner/drop_item/deposit/withdraw`；`bind` 为兼容别名；仅排队，不代表完成 |
| `buddy_places(query?,building_id?,offset?,limit?)` | 查询伙伴确实见过的建筑记忆 |
| `buddy_storage(container_guid?)` | 读取伙伴当前附近箱子的槽位与可用性，不打开、不转移物品 |
| `buddy_recipes(revision, binding_token, query?, recipe_id?, offset?, limit?)` | 查询当前伙伴的服务端配方，校验归属和指令版本，只读 |
| `buddy_result(action_id)` | 查询 `queued/running/completed/failed/interrupted` |
| `buddy_reply(text, revision, message_id, finish?, buddy_id?)` | 指定伙伴说话；完成时仅结束该伙伴贡献并归队跟随 |

以上其余动作、结果、配方、建筑和存取工具也接受 `buddy_id`；有两个伙伴时必须指定 ID。观察 ID、绑定 token、动作结果及交付回执均按伙伴隔离。

`move` 参数为 `{x,z}`，`collect` 为 `{target_guid}`。只能用当前观察提供的资源 GUID；位置与动作由服务器再次检查。`follow` 的完成仅表示进入跟随行为，抵达需通过 `owner_distance` 确认。

`search` 参数为 `{point_id,x,z,products:["cutgrass"],timeout_seconds:8}`；只允许使用当前感知提供的落点，单步最多 20 单位、8 秒，服务器重查陆地、直线路径和已感知危险。途中发现目标资源立即结束搜索步，交给任务层确认并采集。结果 `resource_found/search_leg_arrived/search_leg_timeout` 均不代表库存任务完成。

游戏日志前缀为 `[JEV_COMPANION]`。本机终端显示带伙伴名字的任务表格、`companion_plan_requested` 和错误类型。HTTP 测量写入工程 `logs/companion_transport.jsonl`，不记录正文或模型密钥。

本机 `logs/companion_agent.jsonl` 记录规划请求、接纳的任务、实际可见产物与背包数量、动作 ID、执行结果和具体失败原因，不记录模型 Key 或原始玩家聊天正文。多伙伴增加 `team_plan_requested/team_plan_adopted`，各伙伴事件包含 `buddy_id`。资源实体名与背包产物按当前观察匹配（例如 `grass → cutgrass`、`sapling → twigs`）。未找到资源时优先局部搜索；未开启搜索或没有安全的新落点时解释限制并归队，不再将“未找到资源”累加成三次采集失败。搜索预算耗尽使用共用看板的空闲评估与冷却恢复，不逐步重新规划。
