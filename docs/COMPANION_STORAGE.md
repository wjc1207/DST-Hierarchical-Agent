# 伙伴物品交接和箱子（0.4.2）

玩家通过原版给予操作主动交物品给伙伴；绑定期间打开伙伴自身的原生接收状态，沿用原版 player trader，物品进入真实背包，接收不调用模型。释放时恢复由本模组打开的接收状态。没有读取或抽取主人背包的接口。

## 看板目标

| target | 完成条件 |
|---|---|
| `give_owner {prefab,count}` | 走近实际 RPC 主人，原版给予成功，双方真实数量变化确认，累计交给主人 count 件 |
| `drop_item {prefab,count}` | 在伙伴脚边陆地放下 count 件，核对实际掉落实体和背包减少；不代表主人收到 |
| `receive_item {prefab,count,timeout_seconds?}` | 靠近主人并等待供料，伙伴背包总量达到 count；默认等待 120 秒，可设置 10–600 秒 |
| `inspect_storage {container_guid}` | 当前观察中该箱子内容已知 |
| `deposit {container_guid,prefab,count}` | 累计向指定箱子实际存入 count 件 |
| `withdraw {container_guid,prefab,count}` | 累计从指定箱子实际取出 count 件 |

每个 target 带 `type`。依赖、优先级、专注和 `start_at` 仍由共用任务层处理。先等待材料再制作，用 `receive_item` 作为制作任务的 `depends_on`；玩家把材料丢在地上时，另用普通 `inventory` 目标拾取。

交付／存取／放下的 count 指该任务实际执行的累计数量，区别于库存目标的当前持有总量。修改同一任务数量表示修订累计目标，重新规划要保留 ID；全新的一次重复要求应使用新 ID。不能凭“箱子里已经有三根草”确认“存入三根草”完成。

## 执行与观察

服务端观察伙伴 20 单位内最多 8 个普通箱子或龙鳞宝箱。`containers` 包含 GUID、位置、距离、槽位、空位和物品数量；关闭的箱子可以由服务端直接感知。其他人正在打开、烧毁或不可访问的箱子标记 `contents_known:false`，不是空箱。每个箱子最多回传 40 个槽位条目，`items_complete` 表示是否完整。

主人打开查看也属于占用。0.4.1 对 `chest_busy` 本地等待，关箱后重新检查并继续原来的累计交接，不计失败、不逐次调用模型。存取提交后才遇到占用的竞态同样等待，避免立即使用同一份旧观察重发。连续占用 60 秒没有进展才重新规划，成功转移会重置等待计时；箱子消失、烧毁和满格仍分别处理。

占用快照的 `busy_openers` 回传打开者 GUID 与 `is_owner`，以及原生 `opener_count`；日志 `storage_wait/storage_resume` 记录进入等待与恢复。真实动作进展会重置连续失败计数，短暂占用不会累计成“三次失败后停止”。

交接先进入目标 3 单位内，操作前重查玩家存活、箱子实体、占用状态、物品和容量。给予只能交给自己的实际主人；原料来源限伙伴主背包和穿戴的背包，排除已装备、鼠标拿取、锁槽和嵌套容器物品。接收方满或拒绝时不主动把溢出丢地；箱子插入失败恢复已拆出的一件。存取沿用原生容器过滤、堆叠和开关规则。

0.4.2 在交付、放下和存箱子的目标物品只剩已装备工具时，先自动 `unequip` 收入背包，再继续原交接任务；若另有未装备的同类工具，可直接交出备用物品。卸下不增加交付回执。新制作工具会自动装备，因此“做一把斧头交给我”现在能连续执行制作、卸下、交付，无需中间重新规划。空间不足或装备禁止卸下时保留原装备并报告；背包本体等需要丢地才能卸下的装备不做自动收纳。

底层每次转移一件物品，使用 `{prefab,total_count,task_key}`，箱子操作另加 `container_guid`。服务端以真实变化写累计回执，重复动作达到总量后不再转移；Python 合并结果和快照回执，不重复加数。新消息中断寻路或等待，尚未发生的转移不会继续执行。一个绑定会话最多保留 128 个不同交接任务回执；快照回传最近 32 个，旧记录不淘汰以免重复执行。回执与伙伴绑定一样尚不跨服务器重启持久化。

`buddy_storage(container_guid?)` 是只读 MCP 查询，模型侧同名用途工具为 `query_storage`，不占原生动作队列。等待玩家给予期间只检查观察和超时，不轮询模型；超时再请求规划解释或调整。箱子尚无跨距离记忆，不支持冰箱、烹饪锅或模组自定义容器；新造箱子需先观察到真实 GUID 再规划存取。

## 游戏验证

重进世界并重启本机 Python，先 `/buddy summon`。用鼠标拿着物品对伙伴执行原版“给予”，核对物品进入伙伴背包，再分别测试：

```text
/buddy do 给我三根草
/buddy do 把两块石头放到地上
/buddy do 把三根草存进旁边的箱子
/buddy do 从旁边的箱子取两块石头，然后交给我
/buddy do 等我给你两块燧石，再制作一把斧头
```

最后一项还需满足斧头的其他配方材料；模型应明确等待目标和前置依赖。再测试玩家背包满、箱子满、其他人打开箱子及交接前 `/buddy stop`，确认没有多给、丢失或中断后继续转移。自动测试已覆盖这些执行边界，实际游戏表现仍待验证。
