# 多伙伴 0.7.0

每位玩家最多绑定两个有名字的原版威尔逊。服务端名册提供真实名字、稳定槽位 ID、实体 GUID 和绑定状态，客户端不根据模型回答猜名字。名字是伙伴别名，不改变角色 prefab。

## 使用

更新服务端和客户端模组，重新进入世界，重启本机 Python：

```powershell
python python/mcp_agent/companion_agent.py --execute
```

点游戏 HUD 右侧的「伙伴」打开面板，可召唤伙伴、选择操作对象、切换指令／自主模式和开关聊天监听。名册显示每个伙伴的当前活动。也可以在游戏聊天输入：

```text
/buddy summon 一号
/buddy summon 二号
/buddy list
/buddy ai
@一号 收集三根草，然后回来
@二号 收集两根树枝，然后回来
@一号 @二号 帮我收集建科学机器的材料
@全体 停止
```

不开普通聊天入口也可使用 `/buddy do @一号 ...`。不带 @ 的需求交给统一规划器，在所有已绑定伙伴之间分工；不带 @ 的 stop/follow/stay/release 手动命令作用于所有已绑定伙伴。`/buddy stop @一号` 只停止一号。面板的「停止并待命」和 `/buddy stop` 立即执行，作废该伙伴尚未接纳的规划。聊天框里的 `@一号 停止` 交给模型理解。

名字在首次召唤时设置，1–12 字、不含空白或 @，全体／all／自己为保留名。@ 必须位于正文开头，名字后用空格分隔，支持多个连续 @；未知名字或缺少正文整条拒绝。重复同名 summon 找回同一伙伴；不填名字优先复用第一个，创建第二个必须使用不同名字。释放保留本服务器会话中的名册预约，不用于改名或生成无限伙伴。

## 伙伴自主模式

| 操纵对象 | 指令 | 自主 |
| --- | --- | --- |
| 玩家角色 | 聊天监听开启后输入 `@自己 需求` | 「角色操控」面板编辑目标和开始自主 |
| 伙伴 | `/buddy do 需求` | `/buddy auto 长期目标` |

召唤后输入 `/buddy auto 维持营地箱子里的草和树枝储备`。当前绑定的伙伴共享这个目标，统一规划器按各自状态分配阶段任务。只召唤一人也可以运行。阶段完成后会规划下一批。暂时受阻或当前目标已经满足时，间隔 30 秒再检查。

`/buddy do @一号 给我三根草` 会临时接管一号。一号结束指令后按最新状态继续长期目标。在面板切回「指令」或输入 `/buddy auto off`，会停止队伍的自主工作。已接下的临时指令继续执行，完成后该伙伴回到跟随。切回「自主」或输入 `/buddy auto` 可恢复本次会话上一次设置的目标。

## 规划与执行

服务器按真实 RPC 玩家隔离名册，每个槽位复用已有服务端执行器，分别维护绑定 token、指令版本、动作 ID、心跳和交付回执。客户端一次 HTTP 交换上传整个队伍，各角色状态继续保持独立。

当前模组统一发送队伍快照，单个伙伴也使用同一协议。遇到队伍快照错误时，更新 DST Buddy Agent 并重新进世界。

本机只有一个真实 DeepSeek 规划器。角色需要规划时提交本地请求票据；统一规划器看到所有成员状态、当前看板与带接收者的最近消息，只能修改本轮请求的看板。模型响应的 `assignments` 按伙伴 ID 分组。任务类型和参数直接写在同一对象里，例如 `{"type":"collect","prefab":"cutgrass","count":4}` 或 `{"type":"return_owner","at":"night"}`。采集数量是背包目标总量，新的 `at:"night"` 指下一次入夜。程序补齐常规字段并转换成内部 `team_plan` 和各角色的 `task_board/agent_reply`。复用现有任务时填写其 ID，任务取消用 `cancel_task_ids`。整批先校验角色、能力和任务，程序再用发起请求时记录的控制版本与对话版本校验时效，最后分发给原 `CompanionAgent`；每人最多六任务、两专注任务，沿用共用规划请求和任务调度层。任务依赖只允许引用本人的任务。

动作可以并行。聊天框里发给一号的消息会触发后台重规划，一号和二号继续执行各自看板。纯对话可直接回复；新看板在当前动作结算后按最新状态接纳。连续发消息时，只有最新对话版本的结果可以接纳。仍有效的其他规划请求进入下一批。每次只运行一个模型请求。在队伍指令模式下，角色完成后归队，其他角色继续。全队完成状态必须确认所有仍执行中的角色均完成；只有本轮待规划角色完成而其他成员继续工作时，代码将全队状态保留为 working，同时正常接纳本人的完成回复。各成员的回复随各自看板分发，通过原生发言通道输出。

原来的 `.env`、本地传输配置和 8766 端口继续使用，无需每名伙伴单独启动 Python。各玩家使用自己的 Key，服务器不调用模型。两名伙伴的状态和分工会增加上下文用量，并非每人分别维护一套独立模型对话。

## 定时集合

「天黑时回来」和「天黑前回来」都使用 `return_owner` 任务的 `at: {day: 1, phase: "night"}`。`at` 可以用当天进度 `progress` 代替 `phase`。

服务端随观察上报下一个实际阶段、距切换的游戏秒数，以及白天、黄昏、夜晚的当前时长。执行器用到主人的距离、伙伴跑速和绕路余量实时估算出发时机。实际返程启动后，伙伴进入主人 4 单位内即完成，允许提前到达。接单时已在主人身边的伙伴保留返程任务，到了目标时刻仍在主人身边即可完成。预计迟到和实际错过时间时分别在后台通知 DeepSeek，原定时间继续保留。

## 遇敌撤离

服务端发现附近敌人的战斗目标是伙伴时，会中断当前动作，并选择远离威胁的陆地落点。撤离期间暂停看板动作，脱离锁定后继续原看板。服务器日志记录撤离开始、找不到安全落点、结束以及死亡来源。

## 伙伴本人发言

统一规划器只负责内部分工，不作为聊天角色。每个伙伴在自己的 `assignments[buddy_id].reply` 提供简短的中文第一人称发言。共同任务时各说自己的安排；`@一号` 的回复只交给一号。完成、遇阻和请求玩家供料仍由对应伙伴反馈，不额外生成队伍总结。

Python 按既有任务层调用 `buddy_reply`，服务端由该伙伴实体说话，主人聊天记录显示其真实名册名字。客户端按伙伴与消息 ID 去重；旧版 `team:true` 播报被忽略，不冒充任何伙伴。模组状态、格式错误与连接异常继续使用系统提示。每位玩家仍只有一个真实模型规划器，不因角色发言增加模型调用。

0.6.3 在每个 Wilson 的两端初始化同一个名称网络字段；只有召唤或重新绑定的伙伴写入名册别名。客户端的游戏内显示名称随网络字段更新，真人 Wilson 的字段为空，沿用原有名称。头顶回复使用原生 talker 网络广播，最多 60 字一页，按阅读长度显示 3–8 秒再切换；无额外说话动画，新回复、指令变化或失去绑定后不会继续播旧分页。头顶气泡只在角色正常可见时显示，离开视野仍可查看主人聊天记录。更新后服务端和客户端都需重进世界。

## 共享与冲突

共享各伙伴确实观察过的建筑位置，并保留来源；每名伙伴仍受 64 条建筑记忆上限约束。本地再次观察会更新事实，不复制其他伙伴背包或解锁科技。需要靠近科学机器刷新自己实际可用科技。

采集和砍挖动作在本机临时认领资源实体 GUID；其他伙伴过滤该实体，资源已被认领时本地等待，动作结束、指令改变或过期后释放。箱子继续使用原来的原生容量／占用检查与短暂等待。这不是全局世界锁，也不保证不同玩家的队伍互不竞争。

本版支持各伙伴与主人之间的给予、放下、等待供料，以及箱子查存取。尚未实现伙伴直接交付物品、跨角色任务依赖、跨服务器重启的伙伴存档或跨洞迁移。自主规划使用伙伴当前已支持的动作，适合采集、存箱与制作等补给任务。

## 验证入口

先召唤两名伙伴，查看名字与地图标记，分别指定收草、收树枝，确认同时行动。只给一号新要求，检查二号继续原动作；随后 `@全体 停止`。最后给不带 @ 的共同需求，观察统一规划的分工和各自完成回复。

Python 日志 `logs/companion_agent.jsonl` 包含 `team_plan_requested/team_plan_adopted` 及各角色 `buddy_id`。MCP `buddy_observe()` 返回队伍，`buddy_observe(buddy_id)` 返回单人；两个成员时其余角色工具必须携带 `buddy_id`。角色说话使用 `buddy_reply(..., buddy_id)`，完成仅结束该伙伴的贡献。

0.6.0 首轮实测已验证两名伙伴分工、同时工作和各自完成：一人交付浆果并制作火把，另一人制作斧头、取得并交付木头。该轮未覆盖单独 @ 中断。0.6.1 修复树倒下后组件替换造成的最终一斧误判，动作回执后用新观察继续；规划修复保留团队响应格式，校验错误定位到具体伙伴和字段。模型可用性及正确输出仍需实测。

0.6.4 完成确认保留同 ID、同目标的历史进度，不因采集物已存箱而复活旧采集或返程任务。校验看板直接使用执行器给出的完成视图，不用空执行器重新推算历史。原样保留的已完成存箱任务不要求当前仍看得见箱子；新 ID、增加数量、更换箱子和未完成存取仍需当前观察。真实重复需求用新任务 ID 或修改目标表达。暂停期间重复失联每 30 秒最多记录一次，恢复后写入 cycle_error_end 的持续时间、重复和抑制计数；其他执行异常仍立即记录。


## 外部 MCP 看板

在 DSH 中把仓库的 `python/mcp_server/companion_server.py` 配为 stdio 服务启动脚本。模组连接本机桥接并绑定伙伴后，即可通过 MCP 派活。服务负责展开扁平任务、校验和后台执行。

- `submit_task(task, buddy_id)` 新增一项任务。
- `submit_task_board(board)` 批量合并，双伙伴提交使用 `board.assignments`，按伙伴 ID 分组。
- `get_task_board(buddy_id)` 查看进度和活动动作。
- `update_task(task_id, changes, buddy_id)` 修改任务。
- `delete_task(task_id, buddy_id)` 删除任务并停止它驱动的活动动作。

仅有一个已绑定伙伴时可省略 `buddy_id`。DSH 和内置 Agent 启动同一个 MCP 服务。内置 Agent 在自己的进程调用 DeepSeek。两者都可用 `get_planning_state` 读取控制状态和版本，通过 `submit_task_board` 的 versions 参数提交计划，并用 `send_planning_reply` 发回游戏内回复。
