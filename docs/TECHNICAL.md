# JEV DST Agent 技术说明（1.7.0）

[项目首页](../README.md) · [English technical reference](TECHNICAL.EN.md)

以下命令均从项目根目录（`jev_dst_agent`）运行。

### 1.7.0 本地看板自动推进

执行模式优先按看板优先级、依赖和最新实测进度推进视野内可行任务，每完成一个有界动作就重算目标；连续采草、切换到树枝等过程不请求 JEV，也不发起预测预取。没有本地任务可做时才回到 JEV。新资源出现本身不打断这段执行，清单外机会仍交由 JEV 选择。只读／试运行模式不自动操作。

支持当前库存采集、明确列为任务的斧头／镐子／火把制作、进食和现有合法建筑动作；日志／矿物任务可用已有且耐久足够的工具处理 6 单位内的已知目标并收集掉落物，但不会隐式规划缺失工具。工作目标也必须有安全可达路径，并要求新版 Mod 的 `telemetry.cancel_work` 能力。探索、跨区寻路和清单外采集不自动执行。沿用原有夜间移动、饥饿紧急状态和配方安全约束；例如夜晚只靠固定火堆照明时，不自动离开采集。

自动动作前重新计算合法性并核对任务／目标；读取到敌人瞄准、生命下降或时段／夜间光源变化时交还 JEV，不走失败退避等待。移动按键保持期间每 0.1 秒检查最新已接收遥测，响应速度仍受 Mod 上报速度限制。中断时释放移动键；砍树／采矿另外通过 F4 取消 Mod 后续工作派发，`Ctrl+C` 也走该清理。服务器已开始的单次动画可能仍会结束，不承诺即时撤销。失败或目标进度无实际增加时暂停该看板／任务／目标组合 15 秒并交还 JEV；无关物品变化和饥饿自然下降不算目标进度。

终端显示 `board_auto task=… action=… progress=…`、`board_auto_completed` 或 `board_auto_handoff reason=…`。计时 JSON 标记 `decision_source=board_auto`、`board_task_id`、`board_auto_action`、`board_auto_outcome` 和 `board.auto_execute`；成功自动轮次没有 JEV 请求耗时。更新 Python（含新增 `board_executor.py`）并重启，同时更新、重载 `modmain.lua`／`modinfo.lua`；保留之前版本所需的 `scripts/` 文件。schema 仍为 10。未更新 Mod 时自动砍树／采矿禁用，其他合法本地任务仍可执行。

### 1.6.2 普通花采集

`flower` 接入明确可采状态、可达路径过滤、`collect_flower`、区域资源记忆和新资源事件。采集验证 `petals` 增量或原花消失，流水预测按获得一个花瓣并移除花处理；极快采集仍可回退为完成后预取。`petals` 可以单独拾取，但不加入充饥或烹饪名单。采花只是可选机会，由 JEV 权衡收益，不强制执行；提示提醒同 prefab 的玫瑰外观可能有刺伤风险。`flower_evil` 等其他 prefab 未加入采集白名单。需更新、重载 Mod 的 `modmain.lua` 和 `modinfo.lua`，并同步 `controller.py`、`jev_agent.py`、`action_buffer.py`。

### 1.6.1 联机客户端的开始确认

关闭移动预测时，客户端可能没有本地状态机或 buffered action，旧版因此始终输出 `doing=false`。新版 `scripts/jev_execution.lua` 只读追踪原生 `RemoteActionButton` 和 `RemoteMakeRecipeFromMenu` 实际发送的目标／配方，保留原调用及其返回值，再通过 `IsDoingOrWorking()`、复制的 `doing` 标签或本地状态机确认后续动作状态。仅请求、已有忙碌状态或不匹配的本地动作均不算开始确认。

请求后的观察以每秒 30 次短期轮询进行，开始时主动输出遥测；确认记录在动作状态结束后保留 0.8 秒，未获确认的请求 3 秒过期。Python 按目标／配方匹配，并拒绝早于本次交互的旧请求；这只是开始确认，成功结果仍需单独验证。计时日志的 `buffer_start_source` 和终端 `jev_buffer_predicted ... start_source=replicated_transition` 可确认是否走到了新路径。需更新 `modmain.lua`、`modinfo.lua`、新增的 `scripts/jev_execution.lua`，以及 `action_buffer.py`、`jev_agent.py`；重载 Mod 并重启 Python。schema 仍为 10。

### 1.5.5 多汁浆果支持

修正浆果丛的 prefab 为 `berrybush_juicy`（不是 `juicyberrybush`）。Mod 输出明确的可采状态，使用 `CanBePicked()`（有组件时）和复制的 `pickable` 标签检查；Python 候选要求明确可采且路线可达。采集产物 `berries_juicy` 用于完成验证，新发现和观察到的再生触发探索事件。散落的生、熟多汁浆果均可拾取；`berries_juicy` 和 `berries_juicy_cooked` 进入安全食物名单，生果可在火堆旁烹饪，进食动作沿用先烹饪再吃的组合逻辑。本次需同步 Python 控制端并更新、重载 Mod。

### 1.5.4 边界与入口修正

前沿候选和边界完成度共用同一空间判定：从当前拓扑区域的已观察陆地出发，可沿相邻、已观察可通行但无拓扑标签的连接带寻找尚未观察的邻格，不越过海面或其他已知区域。不为连接带编造区域 ID，也不将其面积计入当前区域。已完全观察的无标签地带本身不再算作未知边缘；完成度仍只是观察网格上的空间完成度，不保证拓扑标签完整。

跨区入口按入口 ID 保存“接近／穿越”状态。抵达来源侧或在入口走廊内越过来源侧后，后续路段保持朝目的侧前进，不因距离来源侧超过到达容差而折返。离入口超过 8 单位时重置接近状态；确认进入另一区域后清空旧状态。每段仍检查地面和威胁，穿越被阻断时不退回来源侧伪造可用路线。此改动需要更新 `modmain.lua`、`modinfo.lua` 和 `scripts/jev_exploration.lua`，重新加载 Mod；遥测仍为 schema 10。

## 输出的游戏状态

客户端 Mod 每秒向 `client_log.txt` 写入一条 JSON 记录，内容包括：

- 天数、昼夜阶段和世界时间；
- 生命值、饥饿值和理智值；
- 背包与已装备物品；
- 当前能否制作火把或营火；
- 附近的有用物品、资源、光源和威胁；
- 持久化的前沿导航状态、目标点和当前路段。

较短的记录以 `[JEV_DST_STATE]` 开头。超过单行日志安全长度的记录会分成多条 `[JEV_DST_CHUNK]` 输出，由 Python 端按编号拼回完整 JSON。游戏日志在每段末尾追加的制表符会在拼接前去掉。控制器和状态监视器只接受完整且可解析的记录；旧版 Mod 留下的截断行会被忽略。

### 动作衔接与等待

1.4.3 增加按需状态刷新：Mod 在 `telemetry.on_demand` 中声明支持后，控制器可通过保留键 F2 请求立即上报，无需等待下一次定时记录。普通新状态等待请求一次刷新；制作、装备、进食等结果验证期间最多每隔约 0.2 秒请求一次，日志轮询间隔为 0.02 秒。原有定时上报仍保留；旧 Mod 未声明支持时继续等待定时记录。

日志读取采用增量方式，保留未完成行和分段 JSON，只解析新追加的数据，并检测日志截断、重建或替换。游戏已在前台时也不再重复等待窗口聚焦。采集发出一次空格后等待完成条件，避免快速状态刷新导致动画未结束就反复交互。移动仍验证松键后的新状态。

这些调整缩短状态反馈造成的停顿。1.4.4 的执行循环默认启用下一决策预取；单次决策和试运行仍按顺序执行。终端的 `decision_time` 表示完整 JEV 请求耗时，`cycle_timing` 表示本轮实际阻塞时间。默认循环冷却为 0；DeepSeek 规划在后台运行。启用按需刷新和边缘绕行需要更新并重新加载 Mod。

### 下一决策异步预取

`--loop --execute` 默认启用预取。探索采用事件驱动：移动中途只读取新状态做事件与安全检查，不按路段请求 JEV，也不在探索结束回调中预取。事件结束当前意图、完成收尾后，下一轮读取最新状态再请求 JEV，让新发现的浆果等资源进入决策候选。采集、进食、烹饪和基础工具制作仍可在完成条件被观测到时提交预取，但短动作的可重叠时间有限。长时间砍树或采矿不会在作业刚开始时预取下一动作。预取结果仍可选择探索，限制的是请求发起时机，而不是下一动作。后台线程只请求模型，不发送游戏输入。`--no-prefetch` 不会关闭探索事件检查。

1.6.0 加入流水式两步缓冲：一个动作执行中，最多提前请求一个下一动作。走向资源或只发送按键不算开始；Mod 的 `execution` 必须提供当前动作状态或 1.6.1 的近期 `confirmed_start`，原生 `PICK`／`PICKUP` 的目标 GUID 或 `BUILD` 的配方必须匹配。控制器随后根据按键前状态预测成功后的背包和目标变化，明确以预测而非观测状态输入 JEV。首批支持草、树枝、普通／多汁浆果丛、已知堆叠数量的散落物，以及斧头／镐子；不预测探索、火把、营火、砍树采矿或进食烹饪组合。

预测请求在当前动作成功返回、实际背包数量和装备归属与预计结果相符后才能使用。失败、预测不符、新资源／观察到的再生、新区域、威胁、受伤、昼夜变化或跨入饥饿紧急线时失效；仅已知资源重新进入视野不算新发现。背包按同类物品汇总数量，堆叠合并不导致误失效。未知开始信号、角色特殊产量／配方、自动装备与预计归属不符时保守回退；无开始信号可沿用完成验证后的普通预取，不假装提前成功。终端输出 `jev_buffer_predicted`、`jev_buffer_confirmed` 和丢弃原因，计时日志记录 `buffer_stage`、`buffer_validation` 以及实际隐藏耗时。

同时最多保留一个预取请求。结果从提交起最多有效 3 秒；上述状态变化或位置改变超过 7 单位时丢弃。执行前重新生成合法候选项，按采集 GUID、目的地区域 ID 或本地前沿目标匹配原选择；寻找新区域按来源区域 ID 匹配意图，不要求临时导航点保持不变。路线排序变化不会把旧的 `travel_region_2` 错当成新目标。无效、失败或过期的结果回退到当前状态的新请求，控制器不会自行选择替代动作。需同步 `action_buffer.py`、`decision_prefetch.py`、`controller.py`、`jev_agent.py`，更新并重载 1.6.0 Mod（`modmain.lua`、`modinfo.lua`）。schema 10 新增可选 `execution` 和散落物 `stack_count` 字段；旧 Mod 缺少它们时不会启用预测。

可加 `--no-prefetch` 禁用预取，进行串行对照。日志中的 `decision_source` 区分同步与预取，`prefetch_request_ms` 是完整请求耗时，`prefetch_wait_ms` 是动作结束后剩余等待，`prefetch_hidden_ms` 是已被其他工作覆盖的请求时间。`prefetch_timing` 单独保存后台请求各阶段的计时，不能再加到当前轮的主线程总时间上。网络请求过慢或状态变化频繁时仍可能停顿。

### 采集路径与暂不可达目标

1.4.5 的状态格式为 schema 9。Mod 为可采集实体添加 `collect_path`：`status` 为 `ready` 时，提供已验证路径长度 `distance` 和下一段 `waypoint`；`blocked` 表示目标所在点不可通行，`unknown` 表示当前观测中没有找到安全陆地路径。`reason` 区分直达、绕行或路径缺失。目标点可站立并不足以证明可达：角色与资源之间的路段也必须通过 `IsPassableAtPoint` 检查。

直线路径受阻时，Mod 在已观测的可通行网格上寻找连接，允许穿过不同地皮，但避开已知威胁；每次状态上报最多构建一次共享的采集搜索树，沿用 2048 格的搜索上限。未知路径不会被判为永久不可达，下一次状态更新会重新检查。

JEV 只获得带 `ready` 路径且未被暂时屏蔽的采集选项。最近目标不可达时，仍可提供同类资源中更远的可达目标；提示同时给出直线距离和路径长度。控制器执行前及每次移动后重新检查路径，并按下一绕行点接近，允许绕行时暂时远离资源。掉落物自动拾取采用相同过滤。JEV 和 DeepSeek 的附近资源摘要也包含路径状态和原因。

连续两段没有移动进展、反复回到旧位置、超过本次接近步数上限，或交互结果验证超时，会按玩家 GUID 和目标 GUID 暂停该目标 30 秒。接近移动每次最多按键 0.5 秒，松键后的新状态最多等待 1.5 秒；反馈超时会以 `approach_feedback_timeout` 暂停目标。此类目标失败返回“跳过”，不触发整个循环的错误退避。角色移动至少 6 单位、目标移动至少 2 单位，或暂停到期后，可在新路径有效时重新考虑。`collection_target_paused` 和计时日志记录原因，接近步骤包含绕行点。资源仍可采集但路径失效时，不会将其误判为采集完成。

需要同时更新 Mod 与 Python：缺少 `collect_path` 的目标不会暴露给 JEV。此限制针对当前已验证路径，不意味着未知区域中的资源永远不能到达。

### 分阶段耗时日志

控制循环默认向项目目录的 `logs/timing.jsonl` 追加每轮记录，终端显示 `cycle_timing` 摘要。用以下参数展开每个子步骤，或指定日志位置：

```powershell
python.exe .\jev_agent.py --loop --execute --timing-details
python.exe .\jev_agent.py --loop --execute --timing-log .\logs\my-run.jsonl
```

记录通过 `run_id`、`cycle`、UTC 时间和所选动作关联，包括状态读取、规划结果检查、候选生成、JEV 请求、动作执行、窗口查找与聚焦、按键、新状态等待、完成验证、循环冷却和错误退避。JEV 请求进一步区分等待响应头、读取响应体和 JSON 解析；等待响应头同时包含建连、网络和服务端处理时间，不能据此单独推算模型推理耗时。砍树和采矿另有指令确认、作业完成、掉落物收集阶段，采集接近过程记录步数、距离和目标 GUID。

`totals` 按阶段汇总调用次数、总耗时、自身耗时和最慢一次耗时，单位为毫秒。`spans` 提供每次调用的开始偏移、持续时间、父步骤和结果；普通日志轮询只做汇总，每轮最多保留 512 条明细，超出数量见 `dropped_spans`。总耗时包含子步骤，自身耗时扣除了子步骤，因此终端的 `action`、`fresh_wait`、`verify_wait` 等不能直接相加。完成验证包含游戏动画和等待状态反馈的时间。整轮时间包含配置的冷却或错误退避，但不包含本轮耗时日志自身的输出时间。

失败、超时、中断、试运行、低置信度放弃和状态变化跳过也会保存；异常记录只包含异常类型。日志不保存 API 密钥、请求头、完整状态或模型原文，并由 Git 忽略。写文件失败会提示，控制流程继续。查看最近一轮的汇总：

```powershell
(Get-Content .\logs\timing.jsonl -Tail 1 | ConvertFrom-Json).totals | Format-List
```

## 有限控制

`controller.py` 支持移动、采集、制作、劳动、进食、烹饪和战斗操作：

```powershell
python.exe .\controller.py status
python.exe .\controller.py move up --seconds 0.25
python.exe .\controller.py interact
python.exe .\controller.py collect grass
python.exe .\controller.py cook
```

`collect` 会选择观测范围内最近的匹配 prefab，通过短促的 WASD 输入接近目标，每次移动后等待新状态，然后按普通动作键。若程序运行被中断，`stop` 会释放所有移动键。JEV 的安全散落资源候选项包括燧石、木头和石头。

采集时，人物会先接近到目标 1 个世界单位以内，再按空格键。若资源来源失去 `pickable` 标记，或散落物从世界中消失，即判定采集成功；如果交互没有完成，控制器会重试，不会直接进入下一轮 JEV 循环。

草丛、树苗和浆果丛会提供明确的实时 `pickable` 值，资源耗尽时不会作为 JEV 候选项。控制器在按空格键前会等待更新的状态，并再次检查相同的值。如果背包中的草、树枝或浆果数量增加，即使采集后的植物实体仍留在世界中，也能证明采集已经完成。

控制器会把所选采集目标的 GUID 保留到执行阶段，避免更近但已耗尽的植物替换原来的有效目标。如果该 GUID 在执行前已不可用，控制器会改选同一 prefab 中当前最近且仍可采集的植物。


测试使用模拟状态和模拟游戏输入，覆盖已耗尽与可采集资源的选择、GUID 传递、后备目标选择，以及植物实体仍存在但背包物品增加时的采集完成判断。

采集移动采用按距离缩放的按键时长：远距离时最长为 1 秒，接近交互范围时最短为 0.04 秒，并等待松键后生成的状态再修正方向，避免旧位置引起反向过冲。正在追击玩家的敌人进入 5 个世界单位内会立即中断采集。遭到近距离追击时，没有武器的角色只会获得逃跑动作；背包中有武器时可以先装备，只有手上已经装备武器时才会出现攻击动作。逃跑在遭到追击时始终可用，包括夜晚。

一次逃跑不是短按一次方向键，而是一个有上限的连续过程：Mod 在追击发生时，沿八种实际 WASD 方向用 `IsPassableAtPoint` 探测最多 6 单位的可通行路线；控制器选择能拉开与追击者距离的方向，必要时沿海岸侧向移动，而不固守“正背对敌人”的方向。每段之后读取角色真实位移并重新选路；若按键后几乎没移动，本次逃跑会避开该方向。无可通行方向时停止并报告错误，不会继续无意义地撞边界。连续两次观测不到追击者时停止，最多执行 8 段。逃跑依赖 Mod 1.4.1 新增的 `navigation.escape_routes`；更新 Python 后也必须更新并重新加载游戏 Mod。

探索现在也会避开近期见到的敌人：Mod 对具有 `hostile` 标签、尚未攻击玩家的实体标记 `potentialThreat`，并记住其位置 90 秒。距离敌人 14 单位内的前沿不参与选择，14–26 单位的前沿有逐渐减弱的分数惩罚；已选目标若变得危险会被放弃。区域路线的下一段也会检查危险范围。控制器在实际按键前再次检查整段路线及最新观测，避免刚逃开又沿原路走回敌人身边。敌人消失后记忆会过期，避免永久封锁区域。

光源管理根据昼夜阶段工作：白天和黄昏不会提供装备火把动作；如果火把已经装备，卸下火把仍是 JEV 可以选择的普通候选项之一。夜晚只有在 8 个世界单位内没有燃烧中的营火或石篝火时，才会提供装备火把动作。营火只能在夜晚建造；如果身边已有燃烧中的营火或石篝火，则隐藏装备火把动作，但仍提供卸下火把动作，不会强制卸下。除非正在逃离迫近的敌人，否则夜晚没有装备火把时不能离开光源移动。

火把操作是带有执行后验证的语义化 Mod 动作：

```powershell
python.exe .\controller.py craft-torch
python.exe .\controller.py equip-torch
python.exe .\controller.py unequip-torch
```

状态数据表明配方可用且硬性安全规则允许时，JEV 候选列表会包含 `craft_torch`，即使背包或手上已有火把。提示显示当前火把总数，供 JEV 权衡备用需求与材料成本；本地看板执行器可把储备目标从 1/2 推进到 2/2，达标后不再自动制作。只有在夜晚、已有火把、火把未装备且附近没有燃烧中的营火或石篝火时，才会出现 `equip_torch`。白天或黄昏装备着火把时，以及夜晚身边有燃烧中的营火或石篝火时，会出现 `unequip_torch`。

`craft_torch` 制作成功后，如果游戏自动把新火把装备到手上，而当前仍是白天或黄昏，控制器会在同一个动作内验证并卸下火把以节约耐久；若已入夜，则保持装备。JEV 不需要为这一步额外选择 `unequip_torch`。

其他有限动作：

```powershell
python.exe .\controller.py craft-axe
python.exe .\controller.py craft-pickaxe
python.exe .\controller.py chop
python.exe .\controller.py mine
python.exe .\controller.py eat
python.exe .\controller.py build-campfire
python.exe .\controller.py attack
python.exe .\controller.py equip-weapon
python.exe .\controller.py flee
```

只有状态数据发现有效的敌对或怪物目标，并且武器已经装备时，才会提供攻击动作。攻击使用游戏原生的 `Ctrl+F`，不依赖鼠标坐标或 Mod 的 F10 桥接。营火建造遵循游戏原生的两阶段流程：先缓冲或制作配方，再放置营火。

砍树和采矿会持续到 Mod 实际选中的目标被完整采集，然后在该目标 4 单位内拾取最多 12 堆掉落物：木头、松果、桦栗、硝石、燧石、金块等常见产物，以及本次作业后新出现的其他散落物。原本就在附近的无关物品不会因此被自动拾取；敌人靠近或夜里没有随身光源时停止拾取。Mod 通过状态中的 `work` 序号、目标 GUID、位置与完成状态向控制器确认，不再让两端独立猜测目标。只有状态数据证明对应的基础工具有足够耐久完成整项工作时，JEV 才会看到相应动作：普通树木按最多砍 15 下保守计算；常见矿石使用游戏定义的 6、4 或 2 次敲击。进食采用保守的前期安全食物白名单，包含烹饪产出的熟肉和熟小肉。

`cook_food` 只在 6 单位内有正在燃烧的营火或石篝火，且背包里有生肉、小肉、浆果或胡萝卜时提供。Mod 再次确认食物带 `cookable` 标记和火源可烹饪，使用游戏原生 `COOK` 动作，一次只处理一份。控制器等到背包熟食数量增加才确认成功；已煮熟的食物和危险食材不会触发该选项。

选择 `eat_safe_food` 时，若已有熟食就直接吃；若只有可烹饪的生食且 6 单位内有可用火堆，则自动先烹饪一份、验证熟食入包，再吃一份。烹饪失败但仍有可安全食用的浆果或胡萝卜时，会退回直接进食；不会把生肉当成安全退路。

## 候选项裁剪原则

候选项裁剪不会替 JEV 选择动作。它只会移除当前不可用、在当前情境中没有意义，或被明确安全约束禁止的动作。JEV 仍会对所有剩余的有意义动作进行排序并选择。

例如，白天或黄昏装备着火把时，会提供 `unequip_torch`，因为收起火把可以节省燃料；没有装备火把时则不会提供 `equip_torch`，因为白天举着点燃的火把没有实际收益。夜晚且没有其他光源时，两者关系反转；站在燃烧中的营火或石篝火旁时，装备火把又会因为重复而被省略。

火堆是固定光源：夜晚没有装备火把时，即使附近有燃烧的火堆，也不会提供区域探索或采集，以免走出照明范围。控制器在移动前和每段移动后再次检查；若途中入夜且没有火把，就停止后续路段或采集步骤。逃离敌人仍可优先于这项约束。

同样，资源耗尽的植物、不可用的配方、耐久不足的工具，以及被世界地图 API 判定不可通行的前沿路段，都不会作为候选项出现。裁剪层只判断哪些操作当前有意义，不判断哪个有意义的操作最好。

## JEV 决策

发给 JEV 的提示区分硬限制与决策建议，并明确每个候选项是一次完整的有界动作：砍树/采矿包含附近掉落物拾取，`eat_safe_food` 在需要时包含先烹饪再吃，单独的 `cook_food` 用于准备稍后食用的食物。提示还提供饥饿比例、可安全食用食物数量和附近可用火源，便于 JEV **快速选择下一步**。JEV 不负责生成计划；1.7.0 起，本地看板执行器可在请求 JEV 前直接推进任务，此机制独立于候选裁剪。

## DeepSeek 每四分之一天规划（可选）

在 `.env` 中填写 `DEEPSEEK_API_KEY` 后，使用 `--loop --execute` 的控制循环会根据 `world.time`（一天内的 0–1 进度）在每天的四个区间各请求一次简短计划：0–25%、25–50%、50–75%、75–100%。启动时若已进入中途区间，会直接为当前区间规划，不补发过去的请求。模型默认是 `deepseek-flash`；可用 `DEEPSEEK_MODEL` 和 `DEEPSEEK_API_URL` 覆盖。规划输入包括当前状态、本次运行中最多 40 条最近行动结果摘要，以及项目根目录的 [DSTKnowledge.txt](../DSTKnowledge.txt)；不会上传逐秒重复的游戏日志。知识文件列出经本机游戏配方脚本核对的常用配方和少量生存常识，可直接编辑；每次规划都会重新读取。程序不打印 API 密钥。没有密钥时仍可单独使用 JEV。

规划请求不会等待在 JEV 的决策路径上：看板未返回时 JEV 照常行动，返回后作为 `task_board` 加入 JEV 的状态输入；旧格式仍兼容为 `daily_plan`。当前游戏事实、候选动作与安全规则始终优先。跨入新区间后旧看板过期，上一季度迟到的回复也不会覆盖当前看板。连续两次执行同一动作失败，或成功建造科学机器后，会触发区间内重规划（至少间隔 60 秒）。若 DeepSeek 因长度截断或空内容无法给出完整 JSON，后台最多重试一次；仍失败时 JEV 继续运行，下一区间再试。行动摘要只保存在当前 Python 进程的内存中，重启后会重新规划。

终端会输出 `daily_plan_requested day=… quarter=… knowledge_chars=…`，完成时输出 `daily_plan_ready`、DeepSeek 请求耗时 `response_time`，以及规划 JSON 的前 240 个字符 `preview`；超长内容以省略号标记。重试时会输出 `daily_plan_retry` 和返回的结束原因；最终失败时也会显示耗时、结束原因和错误。

任务看板的所有任务在最新真实状态中均为 `done` 时，会立即触发区间内重规划，不等待下一个四分之一天。终端输出 `task_board_completed`，随后 `daily_plan_requested ... reason=all_tasks_completed`；DeepSeek 收到最新状态和 `status=completed` 的旧看板，并被提示生成尚未满足的目标。旧看板从当前指导中撤下，但在 CLI／日志保留为已完成历史；新看板返回前 JEV 继续独立决策，不等待请求。每个看板版本只触发一次，同时最多一个规划请求。为防止模型连续返回已满足目标形成循环，相邻的完成触发请求至少间隔 15 秒（第一次立即发起）；新季度请求不受此间隔影响。预测完成、空看板、部分完成、阻塞任务或角色死亡都不会触发这一事件。规划失败后沿用现有“本区间不逐轮重试”的策略，下个区间可再请求。

### CLI 任务看板

DeepSeek 输出 `goal` 与 1–6 个 `tasks`。任务字段包括 `id`、`title`、`priority`（1 最高，5 最低）、`target`、`depends_on` 和可选 `action_hints`／`reason`。目标支持当前库存数量、饥饿比例、已发现区域数、访问已知区域和支持的建筑；不执行代码或自由文本完成条件。重复 ID、未知依赖和循环依赖会被拒绝。DeepSeek 不能自行声明任务完成或填写进度。

库存目标使用 `task_board.py` 的已支持产物名称表，而不是地面实体名称或英文展示名。输入先去除首尾空白、转为小写，再将明确别名 `logs` 规范为 `log`；`rocks`、`twigs` 等合法复数名称保持不变，不进行猜测式单复数转换。未知或当前未支持的库存名称会使该规划校验失败，走已有的有限重试机制，不保留永远无法匹配的任务。任务 ID、标题与依赖不改名。DeepSeek 输入包含同一份名称表及别名映射，进度计算和自动执行均使用规范名称。本修正需同步 `task_board.py`、`daily_planner.py`、`jev_agent.py` 并重启 Python，无需更新 Mod。

每轮由程序从状态计算 `ready`、`in_progress`（目标已有部分进度）、`blocked`、`done`，区间过期时为 `expired`。依赖未完成会显示阻塞原因；库存目标表示当前希望保有的数量，不是累计采集次数，因此物品消耗后可能重新变为未完成。缺少关键遥测时不能判为完成。已验证建造科学机器的事实在本次运行中保留，不要求始终站在机器旁。下一次 DeepSeek 规划也会收到上一张看板及其进展。

终端打印 `TASK BOARD` 表格，列出任务 ID、优先级、状态、进度和标题，下面显示阻塞原因。支持中文显示宽度，不清屏、不覆盖行动日志、不依赖额外 UI 包。看板换版或状态变化立即显示；纯数值进度最多每 3 秒显示一次。完整当前快照保存到 `logs/task_board.json`，变更追加到 `logs/task_board.jsonl`；日志包括本次运行 ID、看板 ID，无 API 密钥。`logs/timing.jsonl` 的 `task_board_id` 和 `ready_task_ids` 可关联决策轮次。

执行模式先用本地看板执行器推进可行任务，详见 1.7.0 说明；没有本地任务可执行或触发安全交接时，JEV 使用完整合法候选自行选择，看板不额外裁剪它的选项。流水预测时按预测库存生成单独的 `state_basis=predicted_success` 看板视图，不写入真实进度，也不能触发自动执行。看板换版或撤销时，旧缓冲失效；启动本地自动执行也会丢弃旧预取。任务全部完成后的重规划沿用上述机制。

将 TypeSafe API 密钥写入 `.env`，格式参见 `.env.example`。默认只进行试运行，不发送游戏输入：

```powershell
python.exe .\jev_agent.py --show-probabilities
```

确认试运行结果后，再添加 `--execute`：

```powershell
python.exe .\jev_agent.py --execute
```

持续自动控制使用：

```powershell
python.exe .\jev_agent.py --loop --execute
```

循环默认没有冷却时间，每个动作完成后会立即重新感知。可使用 `--interval 1` 或其他不超过 60 秒的值增加冷却时间。发生错误时仍会使用至少 1 秒的指数退避，避免形成高速失败循环。

砍树、采矿、采集和建造等长动作会先执行完毕，再开始下一轮，因此动作不会重叠。进入第 2 天不会结束任务：循环会持续运行，仅在角色死亡或按 `Ctrl+C` 中断时停止。瞬时错误会采用有上限的指数退避后重试。

## 区域探索

1.5.0 使用 schema 10。区域以游戏的 `GetTopologyIDAtPoint` 返回值为唯一内部标识，不再按“拓扑 ID + 地皮”拆分。同一区域中杂乱的地皮只是属性，不产生多个区域；相同地皮的不同拓扑区块也不会擅自合并。

JEV 可同时选择以下动作：

- `explore_current_region`：继续搜索当前拓扑区块内的资源与未调查位置。
- `explore_other_region`：寻找新区域，调查当前区块的未知边界；已有其他区域也不会隐藏它。
- `travel_region_N`：前往某个已发现区域，包括返回之前到过的区域。没有单独的返回动作。

Mod 只采样角色附近的拓扑、地皮和通行性。`navigation.graph.current` 提供区域名称、地皮构成 `terrain`、已观察面积 `explored_area`、进入次数、资源和边界状态。名称形如 `forest 1`、`grassland 1`、`grassland 2`；内部 ID 不变，已有编号不会因路线排序而重排。当另一种已分类地皮占比达到 20% 时，区域描述可完善为 `mixed N`，之后不会退回单一地皮标签。面积是去重后观察到的可通行网格数乘以 16，单位为平方游戏坐标单位，不是总面积或探索百分比。

`boundary_complete` 仅表示在当前 4 单位网格精度下，该区块所有已观察陆地格的相邻格均已查明；存在未知格或可通行但拓扑不明的邻格时仍为未完成。完整性不根据前沿暂时不可达、敌人阻挡或寻路失败推断。边界完整时隐藏寻找新区域，但保留前往已知区域。小于网格尺度的狭窄出口仍可能漏检，这不是精确的全地图完成度。

只有实际观察到可通行入口或确认穿越，才记录区块连接；每对区块最多保留三个入口。`navigation.graph.routes` 合并输出可前往的已知区域，支持经过中间区块的多跳路线。每个目的地区别说明实际见过的资源、地形先验、观察面积、是否进入过、边界状态和连接跳数。`distance` 是到下一出口的距离，不能当作到最终目的地的完整路程。执行前仍重新验证下一段路径，远端历史连接不保证此刻安全。

寻找新区域的执行层保存在 `scripts/jev_exploration.lua`，策略由 `navigation.search` 上报：根据未知前沿确定初始方向；方向跨短暂采集、制作保留。前方及两侧偏移路径均受阻时采用固定一侧的沿边绕行，前方重新可通行后恢复原方向。这是局部几何绕行，不会把受阻直接判定为海岸或边界探索完成。记录近期轨迹，发现回环时暂停原目标 30 秒并重新选择方向。道路不再参与探索方向或路线选择。

JEV 决定继续本地搜索、寻找出口或前往哪个区域；Mod 只提出路线，控制器执行并验证已选意图。新版探索采用事件驱动：一次选择可持续执行多个最多 4 单位的导航路段，没有定时、距离或段数触发的强制重选。短路段是感知与导航检查点，不是 JEV 决策边界。提示会保留搜索方向和累计位移；位移包括意图保留期间的实际移动，不等于专门用于探索的路程。

以下事件结束当前探索并交回 JEV：敌人开始针对玩家（即使之前已经看到它）、新潜在威胁或已知威胁逼近危险距离、生命下降、死亡、夜间失去随身光源、昼夜阶段变化、携带安全食物且饥饿危险、发现或进入其他拓扑区块、抵达目的地区域，以及路径失效、无进展或回抽。系统只停止移动，不自动改为采集、攻击或逃跑。

新资源必须属于支持采集的类型，且当前可采集、路径已验证可达。按玩家和资源 GUID 去重：已知浆果或资源离开视野后重新出现不会重复中断；不可采集的空浆果丛、已采草和隔海不可达的物品不触发。缓存最多保留 4 个玩家、每个约 8192 个资源，超过容量后重建；进程重启或游戏时间回退时重新建立记忆。不要求先走满某个距离才响应新浆果。执行前还会对比模型实际看到的状态，避免将请求期间才出现的资源误当作 JEV 已考虑过。

已知植物明确被观察到 `pickable=false` 后，再变为可采集且可达时，触发一次 `resource_available_again`，覆盖浆果、草和树苗等再生资源。普通状态读取会记录采空，因此采集、制作等其他动作期间也不会漏掉这次变化。仅离开视野、未知的采集状态或路径失效不会被当成采空。若再生时暂时不可达，事件保留到路径可用；若 JEV 的决策状态中已经看到了再生资源，则视为它已考虑过，不重复中断。采空时间戳用于防止旧决策状态误消耗更新的再生事件。完全发生在视野外、从未观察到采空的再生，不能仅凭 GUID 推断。

终端输出 `exploration_yield reason=new_resource prefab=berrybush guid=... legs=... distance=...` 等交回原因；耗时日志记录 `exploration_event`、连续段数和距离。正常连续探索中不会逐段提交 JEV 预取。事件监测位于 `exploration_events.py`；这次事件驱动调整只需要同步 Python 文件，沿用 schema 10 Mod。

当前区域搜索仍使用局部前沿：一个已知可通行、属于当前拓扑区块且邻接未知格的格子称为“前沿”。基础评分为：

```text
score = information_gain * 10 - distance * 0.5 - visits * 6
```

分数最高且可到达的前沿成为本地搜索目标，跨采集和制作保留；区域改变、到达或路径失效后重新选择。新区域搜索另用持续方向、信息增益、访问次数、距离和沿边方向评分，不直接复用本地搜索排序。每次最多尝试 24 个出口候选，绕行搜索树最多检查 2048 个格子。危险目标与移动路段仍会被裁剪。

所有新版探索动作连续执行经过验证的短路段，允许 1.5 单位到达误差。Mod 每隔 0.75 单位使用 `TheWorld.Map:IsPassableAtPoint` 检查路径，控制器执行前再次检查危险距离与夜间照明。F1 是新增的出口搜索失败反馈键，不是 JEV 的独立动作；连续两次尝试没有进展时只暂停相应搜索点，不改变本地搜索目标。1.5.2 已移除道路扫描、道路图、沿路执行器及 F4 反馈，不再因发现道路而打断探索。旧版道路数据不会生成候选项，旧版沿路动作会在输入前被拒绝。

方向键只是根据目标向量推导出的执行细节。移动时按约 6 单位/秒的基准跑速提前刹车，4 单位路段不再固定按满 1 秒。`--move-seconds` 是移动时长倍率和单段上限，默认值为 1，可用范围为 0.2–2.0；加速、减速或角色变化时可调节此值。

已知区域移动也会检测近期回抽并暂停路线 30 秒。耗时日志包含区域 ID、名称、观察面积、搜索策略及移动起终点。区域记忆只保存在本次世界内存中，重进世界会重新观测。升级时请同步更新 Python、`modmain.lua`、`modinfo.lua` 和整个 `scripts` 文件夹，并重新进入世界。

Python 测试仍使用 `python.exe .\run_tests.py`。新增 Lua 离线模拟可使用 `npx.cmd --yes --package=fengari-node-cli fengari tests/exploration_spec.lua`；首次运行需下载测试器。它验证纯导航策略和 Lua 编译，不等于 DST 引擎内验收。

### 只剩等待时的导航诊断（1.5.1）

`confidence=1.0` 不一定是模型偏好等待。若当时只有 `wait` 可选，终端额外打印 `only_wait_available`，耗时日志的 `decision_candidates` 保存实际送入模型的动作列表、前沿状态、未知出口状态、已知区域数、路线数及 `path_diagnostics`；`candidate_rejections` 记录 Python 安全规则删除动作的原因。正常存在其他候选项时，不会误报为“只能等待”。

Mod 的 `navigation.diagnostics` 按前沿、路径树、区域入口、出口搜索和威胁记忆记录计数。例如 `direct_hazard` 表示直达下一段遇险，`no_observed_start` 表示缺少安全起始网格，`no_safe_observed_gateway_path` 表示当前观察中找不到安全入口路径，`search_budget_exhausted` 表示触及搜索上限，不等于物理不可达。

区域路线在直达下一段被危险阻挡时也会尝试绕行，不再仅在地面不通时绕行；前沿也不再仅因远端目标的直线穿过危险而丢弃。绕行允许经过其他已观察的拓扑区块，区块标签不是物理墙；实际跨区仍触发事件并交回 JEV。路径树在一次上报内由前沿、区域路线与采集共享，保留 2048 格搜索上限。各路段仍验证通行性、14 单位危险半径和 20 单位接近限制，控制器执行前再次检查；没有安全路径时仍允许只剩等待。

威胁记忆原有 90 秒期限不变。只有旧位置位于扫描半径内侧、附近实体列表未达到截断上限且本次未发现该 GUID，或实体已不再构成威胁时，才提前清除；扫描范围以外的历史敌人不会凭空消失。动态危险导致失败不会被当成地面障碍加入前沿的 30 秒黑名单。此修复需要更新 Mod（包括 `scripts`）和 Python，并重新进入世界。

### 路径推进与入口稳定（1.5.3）

前沿、区域路线和采集绕行统一采用路径前视：从有序路径后向前寻找 8 单位内可安全直达的路径点，不再机械追逐最近的 BFS 起始网格。实际探索每段仍最多走 4 单位，前视捷径会重新检查完整路段的地面通行性和危险距离，不能切过海岸或敌人。

同一来源区块到相邻区块优先保留上次有效入口，避免距离微小变化引起入口切换；每次仍重新计算路径和安全性，原入口不再可用时才改选有效入口。多跳路线携带真实的 `gateway_id`，耗时日志也记录此标识。控制器因回抽或停滞暂时屏蔽目的地区域时，事件原因显示 `route_paused`，不再混同于 Mod 没有路径的 `path_unavailable`。导航只推进 JEV 已选的意图，不自动更换目的地区域。

装备火把采用与手动点击背包火把相同的物品格动作，而不是动作系统的自动装备辅助功能。

## 执行阈值与安全规则

JEV 提示还明确建议白天和黄昏卸下火把，以节省耐久。

饥饿低于最大值的 30% 且背包已有安全食物时，等待、探索和可选采集会从候选项中移除；JEV 仍需选择下一步，但此时只保留进食，以及确有需要时的逃跑或夜间照明。普通和紧急进食都不受置信度门槛限制。没有携带食物时，不会禁止寻找食物的探索动作。

默认执行阈值：

- 攻击：`0.45`，且没有装备武器时不可用；
- 所有非攻击动作：`0.00`，取消置信度门槛，但保留合法性、路径与安全检查。

`--min-confidence` 仅覆盖攻击阈值，不再影响非攻击动作。置信度仍输出到日志。夜晚没有装备火把时，硬性安全规则会阻止移动或采集；逃离迫近敌人是唯一例外。Git 会忽略 `.env`，发布压缩包也会刻意排除该文件。
