# 添燃料

DeepSeek 可向营火 `campfire` 和石头火堆 `firepit` 添加指定数量的常用燃料，
也可给仍存在的熄灭石头火堆重新点火。使用游戏原生 `ADDFUEL`／`ADDWETFUEL`，
不直接改燃料组件。JEV 候选范围保持原样。

## 看板任务

先通过 `query_places` 取得实际建筑 ID，再指定燃料与比例目标：

```json
{
  "id": "fuel_camp",
  "title": "Maintain camp fuel above 30%",
  "priority": 1,
  "duration": 0.25,
  "target": {
    "type": "refuel",
    "building_id": "building:实际GUID",
    "fuel_prefab": "log",
    "at_least": 0.3
  }
}
```

`at_least` 是 `(0,1]` 内的比例，`0.3` 表示 30%。省略 `duration` 时，补到目标后完成一次；填写后，在该游戏时长内持续维护。达标时为 `maintaining`，让出执行权和专注范围；低于目标时恢复补料。开始时间和依赖满足后计时，包含前往火堆和避险的时间；到期下界仍达标则完成，否则为 `expired`，返回原因。观察不到当前火势时，历史建筑记忆不能证明已达标。游戏暂停不推进计时，重启 Python 不恢复旧计时。

普通客户端不能精确读取燃料组件，仅能读取火焰档位。按照游戏原生四档划分，显示保守估算范围：

| 档位 | 燃料比例区间 |
|---|---|
| 0／熄灭 | 0% |
| 1 | (0%, 25%) |
| 2 | [25%, 50%) |
| 3 | [50%, 75%) |
| 4 | [75%, 100%] |

**只有下界达到目标才能确认完成。** 目标 30% 时，第二档无法确认，需要第三档（下界 50%）。因此实际补料可能超过目标，一次原生动作仍只加一份。若档位未知则暂停，不编造百分比。第四档无法区分 75% 与 100%，纯客户端超过 75% 的目标会报告 `fuel_ratio_unverifiable`，停止继续投料。建议选择 25% 或 50% 等容易确认的目标。

`fuel_percent` 仅在确实读到原生组件值时提供；普通客户端留空。状态中的 `fuel_min/max`、`fuel_estimated` 和看板的 `fuel estimate [...]` 明确区分范围估算与真实读数；若实际组件百分比可读，优先使用该读数。

比例目标使用独立的 `add_fuel_ratio:<GUID>:<燃料>` 原生选项。它可在旧规则认为低火已足够时继续补到目标，但仍逐份复查温度、复制等待和当前区间。体温过高或仍在降温时禁止投料，每次添料后等待至少 2 秒状态更新。达到第四档但无法证明更高比例时禁止反复投料。

燃料限 `log`、`charcoal`、`pinecone`、`acorn`、`twiggy_nut`、`twigs`、`cutgrass`，不自行替换或烧掉活木、装备。湿燃料使用原生 `ADDWETFUEL`。材料不足时由 DS 显式安排采集；携带燃料但距离不足时，自动靠近指定建筑，再按需添料。返回家不等于靠近该火堆，到达不记为添料成功。

任务支持 `start_at`、依赖、专注及可选 `duration`，暂不支持 `end_at`。比例目标不能同时提供 `count`。旧看板的 `count` 任务仍按累计总份数执行（1–10，默认 1），避免破坏已有记录，但 DS 不再创建新的按份数目标；旧 `count` 不接受 `duration`。已经实际添加的份数作为 `fuel_added` 保留用于诊断，不作为比例任务完成条件。

原生添料完成仍要求：精确目标上的原生动作确认开始、指定燃料实际消耗、同一火源燃烧。健康火势使目标达标时，宿主等待这一原生确认，不提前取消导致丢失实际添料记录；持续窗口到期仍正常取消未完成动作。

原生 `auto_execute=true` 不支持此任务。JEV 决策范围保持原样。

## MCP 与状态

`get_state` 的 `refueling.options` 暴露当前可用的具体火源、燃料物品 GUID、原生
动作和 `planner_only=true` 标记。`get_available_actions` 中的选项键为
`add_fuel:<火源GUID>:<燃料prefab>`，也可用专门工具：

```json
{"name":"add_fuel","arguments":{"building_id":"building:实际GUID","fuel_prefab":"log","observation_id":"本次观察凭据"}}
```

返回动作 ID，使用 `get_action_status` 确认结果；支持正常取消。Lua 在执行时复查
原建筑、原燃料物品和原生动作，不静默替换目标。遇敌、驻留边界和观察过期检查继续
有效。驻留期间仅允许安全的本地火堆靠近路线，按目标位置、路点和整段路径长度
检查范围；区域路线估计不能替代本地路径证明。普通探索仍被驻留约束禁止。
夜间靠近仍要求已装备火把，携带火把不等于装备，不自动改变夜间行动授权。

达到低火档、体温预警或等待火势复制更新时暂停投料；已添加份数保留，未添加份数不会假完成。详见[温度安全与火势控制](THERMAL.md)。

此动作表示添入指定份数，不保证燃烧到天亮；客户端没有可靠燃料百分比时不估造
剩余燃烧时间。提灯、矿工帽和其他设备的补充暂不包含在首版中。

## 更新与验证

同步 Python、`scripts/jev_thermal.lua`、`scripts/jev_refueling.lua`、原生执行器、执行观察器和
驻留边界模块后，重新进入世界并重启 Python 控制程序。

离线验证：`python run_tests.py`；Lua 新增 `tests/refueling_spec.lua`，覆盖原生兼容性、
湿燃料、熄灭火堆、背包材料、目标变化、完成校验、取消和驻留边界。另有真实模组
到达距离回归及 Python“靠近后连续添两份”的完整控制循环测试。实机还需确认
服务器复制延迟下的添燃料及重新点火效果。


建筑副本重新加载后，任务 `building_id` 保持稳定；火势遥测和新动作绑定当前客户端 `guid`。旧 GUID 动作会拒绝执行，下一次调度使用新的观察和绑定；详见[建筑记忆](PLACES.md)。
